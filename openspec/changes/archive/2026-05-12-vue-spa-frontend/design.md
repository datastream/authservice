## Context

The authserver currently serves HTML pages via Go templates (`login.html`, `signup.html`, `auth.html`, `tokens.html`) with inline CSS and vanilla JS. A Vite+React scaffold exists in `frontend/` but is never wired to the Go server. The login form submits via traditional POST but the server returns JSON with a `redirect` field — the browser renders raw JSON instead of following the redirect. Error messages have no UI display on login/signup pages.

The service handles OAuth 2.0 authorization code flow, user authentication (session-based + AWS HMAC), and token management. All of this runs on a single Go server using Gin.

## Goals / Non-Goals

**Goals:**
- Replace all Go HTML templates with a Vue 3 + TypeScript SPA
- Convert login/signup/logout endpoints to JSON APIs under `/api/*`
- Go server serves the built Vue SPA static assets and exposes only APIs for auth-facing endpoints
- Preserve existing OAuth server endpoints (`/oauth/*`) unchanged for external clients
- Support SPA-aware OAuth consent flow (session check before rendering consent page)

**Non-Goals:**
- Migrating OAuth endpoints (`/oauth/*`) to SPA — these stay as Go handlers (browser-based OAuth flow)
- Moving away from go-session cookie-based authentication
- Implementing OIDC ID token / implicit flow
- Adding social login providers
- Converting the FGA admin endpoints to SPA (keep as-is for now)

## Decisions

### Decision 1: Vue 3 Composition API + Vite (not React)
**Rationale:** The frontend scaffold already uses Vite, TypeScript, and Tailwind. Switching from React to Vue avoids rewriting all components while keeping the same build tooling. Vue 3 Composition API provides a similar DX to React hooks. Tailwind is framework-agnostic so existing config is preserved.

### Decision 2: Hybrid Vue SPA + Go OAuth consent page
**Rationale:** The OAuth consent flow (`/oauth/authorize`) requires the Go server to check session state and render a minimal "Allow" form. The SPA handles this by:
1. Checking `/api/me` on mount
2. If not authenticated, redirecting the browser to `/login` (SPA route)
3. Once authenticated, the Go template renders the consent button with session data already available to go-oauth2

This is simpler than trying to make the OAuth library work with a pure SPA consent page, since the go-oauth2 library expects a full HTTP request/response cycle.

### Decision 3: `/api/*` prefix for SPA-facing endpoints
**Rationale:** Separates SPA APIs from public OAuth endpoints. Clear URL namespace distinction:
- `/api/*` — SPA-facing (login, signup, logout, me, tokens)
- `/oauth/*` — OAuth 2.0 server (unchanged)
- `/api/v1/fga/*` — FGA admin API (unchanged)

### Decision 4: Build output to `cmd/oauthservice/static/`
**Rationale:** The existing Vite config already builds to `../static/` relative to `frontend/`, which resolves to `cmd/oauthservice/static/`. The Go server serves static files from this path. Minimal config change needed.

### Decision 5: SPA authentication pattern
**Rationale:** The SPA will use cookie-based auth (existing go-session infrastructure). Login/signup POST endpoints return JSON `{"ok": true}` — no redirect field. The SPA navigates to `/oauth/authorize?client_id=...` after successful login using Vue Router. The `/api/me` endpoint is called on app mount to determine if the user is authenticated.

### Decision 6: Remove `ServeStaticHTML` and template rendering
**Rationale:** The Go server becomes purely API + static asset serving. All HTML is generated by the Vue SPA build. The only remaining Go-rendered HTML is the OAuth consent page (minimal, uses `template.ParseFiles`).

## Risks / Trade-offs

| Risk | Mitigation |
|------|-----------|
| Vue SPA + Go session cookies: CORS config must include `AllowCredentials: true` (already set) | Verify CORS allows all SPA API requests; ensure cookie path covers `/` not just `/login` |
| OAuth consent flow breaks if SPA navigates before Go template loads | SPA checks `/api/me` first; if unauthenticated, browser-level redirect to `/login` (not SPA navigation) |
| Existing direct URL access to `/login` or `/signup` returns 404 | Add a fallback route that either redirects to `/login` (SPA) or shows a "Login" button |
| Token management page currently uses fetch + JSON — moving to Vue requires re-encoding the logic | The Vue token manager will be a direct re-implementation of the existing `tokens.html` JS logic |

## Migration Plan

1. **Phase 1 (Vue auth pages):** Create Vue login/signup pages, update Go login/signup endpoints to return `{"ok": true}`, add `/api/me`, wire Vue router, build and serve SPA from Go.
2. **Phase 2 (OAuth consent + logout):** Update `/oauth/authorize` to handle SPA-aware session check, update logout handler to return JSON.
3. **Phase 3 (Token management):** Port the Vue token manager page, wire up the Go token API under `/api/*`.
4. **Phase 4 (Cleanup):** Remove Go HTML templates, `ServeStaticHTML`, unused Go template code.

## Open Questions

1. **Should the root `/` route serve the SPA or redirect to `/login`?** — Default to serving the SPA, which then checks `/api/me` and redirects to login if unauthenticated.
2. **How to handle deep-links to `/oauth/authorize` from external OAuth clients?** — The Go server should detect if the request is from a browser (Accept: text/html) and serve the consent template; if from the SPA (Accept: application/json), call `/api/me` first.
